## 一、操作目标的具体定义

**总目标**：以真实用户操作路径，对当前已实现的功能做一次全流程体验测试，验证「题库管理闭环」端到端可用，并留档每一步的可追溯证据。

**具体目标（可验证）**：

| 编号 | 目标 | 验证标准 |
|---|---|---|
| G1 | 5 种题型均可通过 UI 录入并正确保存 | 每题保存后详情接口返回的 payload/answer 与录入一致 |
| G2 | 列表多维筛选/检索符合预期 | 每种筛选条件组合返回结果数与预期一致 |
| G3 | 客观题即时判分行为符合 DESIGN.md §6 | 单选全对全错、多选漏选按比例给分、填空全角/大小写归一化生效 |
| G4 | 导入导出往返无损 | 导出 → 修改 → 导入后，导入报告数字与预期一致 |
| G5 | 软删/硬删/批量操作行为正确 | 软删题默认列表不可见但仍可查；硬删后 DB 无残留 |
| G6 | UI 交互无明显阻断性缺陷 | 全程无 JS 报错、无死链、无提交后无反馈的按钮 |

**范围边界（如实声明）**：当前代码仅实现 M1/M2——Dashboard、题库列表、题目编辑器、导入导出页；后端仅 questions/categories/tags/import_export/judge 五组 API。**练习会话、答题页、错题本、统计（M3–M5）尚未实现，不在本次测试范围**，仅作为"后续待补"观察项记录。

## 二、涉及的体感动作类型

本次测试将用到的操作动作分六类，执行记录按此分类标注：

| 动作类型 | 代号 | 典型动作 |
|---|---|---|
| 页面导航 | NAV | 打开 URL、点击侧边栏菜单、面包屑返回 |
| 数据录入 | INPUT | 表单填写题干/选项/答案、Markdown 输入、下拉选择分类 |
| 选择交互 | SELECT | 单选/多选勾选、标签选择、难度选择、批量勾选行 |
| 提交确认 | COMMIT | 点击保存/提交按钮、确认弹窗、导入确认 |
| 检索筛选 | FILTER | 关键词搜索、题型/难度/分类/状态筛选组合 |
| 数据核验 | VERIFY | 截图取证、API 响应比对、SQLite 直查交叉验证 |

## 三、执行方式与取证手段

- **双通道执行**：主通道用浏览器自动化驱动真实 UI（localhost:5173）完成体感操作；辅通道用 API 调用（curl）做数据交叉核验，UI 表现 ≠ 数据正确，两者都要取证。
- **证据留存**：每个步骤记录到执行记录表（见第五节格式），含截图文件名 + API 响应摘要；截图存 `docs/evidence/` 目录。
- **环境基线**：执行前记录题目/分类/标签数量快照，执行后对比，确保测试数据变化全部可解释。

## 五、执行记录与总结格式（执行阶段使用）

**每步记录格式**：

| 字段 | 说明 |
|---|---|
| 步骤 ID | 对应第四节编号，如 D1 |
| 计划动作 | 原计划内容（一字不改） |
| 实际执行 | 实际做了什么 |
| 实际结果 | 观察到的现象 |
| 证据 | 截图文件名 / API 响应摘要 / SQL 查询结果 |
| 状态 | ✅ 符合预期 / ⚠️ 有偏差（可继续）/ ❌ 阻断（需停下决策） |

**执行总结格式（全部完成后输出）**：

1. 成功完成的步骤清单（ID + 一句话结果）
2. 出现偏差的部分（步骤 ID、现象、初步原因、对目标 G1–G6 的影响）
3. 后续需要调整的内容（代码缺陷 / 体验问题 / 未实现的 M3–M5 缺口，按优先级排序）

**执行纪律**：严格按第四节清单顺序执行，不跳步、不临时加戏；某步 ❌ 阻断时，先评估是否影响后续步骤可独立性再决定继续或停；任何与计划的偏离都在记录表中显式标注，禁止事后美化。
